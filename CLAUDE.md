# Dance Club Availability Management System

A web app for a VIT college dance club. Core Team members use it to manage members, their weekly academic timetables (who is free when), work reports, OD (On Duty) requests, events, and FFCS grades.

## Member model

- `category`: `CORE` | `MEMBER` | `DANCER` | `FFCS_ONLY` (display: Core Member, Normal Member, Dancer, FFCS Only).
- `isFFCS`: boolean, independent of category: Core, Normal members, Dancers and Dance Leads can all be FFCS. `FFCS_ONLY` always has `isFFCS = true`. Set it on the committee Add/Edit member form, on the Dance Floor roster (Add dancer checkbox and the FFCS column, via `PATCH api/dance/members/[id]/skill` with `{ isFFCS }`, SuperAdmin or the team's Lead), or by the "FFCS Enrolled" column (Yes/No) in both Excel imports and the roster export/template.
- `position` (nullable) and `team` (nullable) come ONLY from `src/lib/teams.ts`, the single source of truth. Don't create a separate positions file.
  - CORE: `position` from `CORE_TEAMS`, `team = null`
  - MEMBER: `position` from `MEMBER_TEAMS`, `team = null`
  - DANCER: `team` from `DANCER_TEAMS`, `position` from `DANCER_ROLES` ("Team Leader" | "Normal Dancer")
  - FFCS_ONLY: no position
- **`team` = dance team for ANY category.** Core members, the SuperAdmin, Normal and FFCS-only members can also dance in one team (`team != null`). Non-DANCER members in a team are always Normal Dancers; Team Leaders are always `category = DANCER`. `danceTeamFor(category, team)` in `teams.ts` validates it. "Dancers in team X" queries use `{ team }` (`inDanceTeam` in `lib/dance.ts`), never `{ category: "DANCER", team }`.
- `components/ui/TeamSelector.tsx` renders the dance-team radio list.
- **Programme / course (`department`)**: chosen from the OFFICIAL VIT Chennai list in `src/lib/programmes.ts` (`PROGRAMME_GROUPS`, grouped B.Tech / Integrated / Law / Business / Science & Design / Postgraduate) via `components/ui/ProgrammeSelect.tsx` (committee Add/Edit, Dance Floor Add dancer, the member's own `/programme` page). "Other" stores `Other: <text>`. `normalizeDepartment()` returns `ok=false` (no label) for anything ambiguous ("Computer Science", "Law", "B.Sc", plain "BBA" because old rules turned "BBA LLB" into "BBA"), a club team/school ("Outreach", "VITBS"), or not offered here; those are NEVER guessed. `lib/programme-issues.ts`: `listProgrammeIssues` (live, no extra column), `notifyProgrammeIssues` (notification type `PROGRAMME_FIX`, link `/programme`, never twice; called after imports and add/edit), `resolveProgrammeIssue` (deletes the notification once the course is valid; called by `api/account/programme` and member edit). `ProgrammeFixBanner` shows at the top of the Dance Floor, console and member profile only for affected members. Analytics groups by programme group and keeps unresolved members under "Needs fixing". Free text is still parsed (imports) by `normalizeDepartment()` in `src/lib/departments.ts` (e.g. "BBA Hons", "BBA HONS", "BBA Honours" -> "BBA (Hons)"; "B TECH : CSE-CORE" -> "B.Tech CSE (Core)"). Add new programmes/branches there, then run `npx tsx src/lib/departments.check.ts`. Law degrees are matched BEFORE BBA (`lawDegree`: "BBA LLB (Hons)", "BA LLB", "Law"), B.Com is its own degree, and specialisations (Quantum Computing, Cyber Physical Systems, Business Analytics, ECM, VLSI, Electric Vehicles) must never collapse into "CSE (Core)" / plain branches. Spreadsheets with personal data never go in `public/` (served publicly; `public/files/` is gitignored); keep them in `C:\Projects_DC\import-files`. Phone numbers are standardised the same way by `normalizePhone()` in `src/lib/phone.ts` (plain 10 digits; check with `npx tsx src/lib/phone.check.ts`). ## Timetable

`src/lib/timetable.ts`: days MONDAY–FRIDAY (no Saturday), slots T1–T12 plus a non-editable `Lunch` column (01:25–02:00 PM). Status is only `FREE` (green) or `CLASS` (red). One `TimetableEntry` row per member+day+slot, unique on `[memberId, day, slot]`. A missing row means FREE. **"Has filled in a timetable" = at least one CLASS row** (`HAS_TIMETABLE` / `NO_TIMETABLE` / `hasFilledTimetable` in `lib/timetable.ts`); members with no rows or only FREE rows (cells toggled back, or rows from an older version) count as "No timetable". Use these everywhere (dashboard tile, Timetable tab, committee Analytics, Dance Floor Availability); never `timetableEntries: { none: {} }`. `components/timetable/TimetableGrid.tsx` is a spreadsheet layout: days are rows, slots are columns, the day column is sticky, and it scrolls horizontally inside its own container only. Each cell saves on its own (`POST api/timetable/[memberId]`); a refused/failed save (checked with `res.ok`) puts the cell back, shows a toast and "Last change not saved". With a mouse you can drag across cells to paint them all to the first cell's new status (touch keeps tap only, because dragging there scrolls the grid). A mouse press switches the cell on pointerdown and the `pressed` ref stops the following click switching it back; taps and Enter/Space go through onClick. Cells have aria-labels (day, slot, time, status). Optional `onChange(classKeys)` lets a parent follow edits (the directory row preview).

## Business rules

**Reports**
- A report needs a description, a work date, and a proof image (required).
- Reports start as PENDING.
- An ADMIN or SUPERADMIN approves or rejects (rejection reason is optional). Nobody can review their own report.
- Images are stored privately in Supabase. `imagePath` is saved, and signed URLs (30 min) are generated when admins view the report. The image is deleted from storage after review.
- Reviewing creates a Notification for the member.
- The reviewer's name and position are shown on the report.

**Passwords**
- Accounts made by the Excel/Google-Form import use the (capitalised) register number as a TEMPORARY password; accounts added through the Add form use the password the admin/Lead typed. Both set `User.mustChangePassword = true`.
- Middleware sends any user with that flag to `/change-password` until they pick their own (min 8 chars, not their register number). After changing, they are signed out and log in again. Anyone can also change it later from the key icon in either sidebar.
- Forgotten password: the SuperAdmin uses "Reset password" on the Edit member page (`components/members/ResetPassword.tsx`, `POST api/members/[id]/password`, SuperAdmin only, not on their own account). It sets the password to the capitalised register number with `mustChangePassword = true` and shows it once so it can be sent to the member.
- **Idle logout after 10 minutes**: `components/IdleLogout.tsx` (mounted in `app/providers.tsx`) watches mouse/keyboard/touch/scroll, shares the last-activity time across tabs via `localStorage` (`dc-last-active`), renews the login every 2 minutes while active, and signs out to `/login?idle=1` (login page shows a message). Server backstop: `session.maxAge = 10 * 60` in `lib/auth.ts` (covers a closed browser or sleeping laptop). Change both together.
- **Closing every tab logs you out** (`lib/tab-session.ts`): each open tab keeps a heartbeat in `localStorage` (`dc-tabs`) and removes it on `pagehide`; `sessionStorage` (`dc-tab`) marks tabs that are already signed in, so a refresh is fine. An inline script in `app/layout.tsx` runs before paint: a NEW tab with no live sibling tab gets `<html data-locked>` (hidden by `globals.css`) and `IdleLogout` signs out to `/login`. Opening links in new tabs works while another tab is open. A crashed browser's heartbeat lingers up to 90s.
- Login is case-insensitive on email. Import accepts our template columns AND Google Form columns (`Email Address`, `Core Position`, `Member Position`, `Dance Team`, `Dancer Role`); duplicate email or register number (any case) is skipped. Speed: the committee import looks up every existing account in ONE query (`existingAccounts`), also skips someone listed twice in the same sheet, and creates accounts 4 at a time (`inBatches`); temporary passwords are hashed at bcrypt cost 10 (`TEMP_PASSWORD_COST`, ~4x faster; real passwords stay at 12); both import routes set `maxDuration = 60` so Vercel never cuts a big import off part-way (88 rows ~10-15 s).

**Dancer section** (`/dance`, `category = DANCER`)
- Login sends dancers and Dance Leads to `/dance`; middleware keeps them out of committee pages (`/dashboard`, `/members`, `/search`, `/analytics`, `/reports/review`). **The Working Committee console is SuperAdmin + Core only.** Because the login token is stale until the next login, `app/(dashboard)/layout.tsx` and both `app/timetable` pages re-check `isCommittee` from the database (Dance Leads -> `/dance`, Normal/FFCS members -> `/profile` or their own timetable).
- "Committee" = SUPERADMIN or an ADMIN whose category is not DANCER (`isCommittee` in `lib/dance.ts`). Dance Leads (`position = "Team Leader"`) are ADMIN but NOT committee.
- **Advisory = read-only SuperAdmin view of the Dance Floor.** A Core member with `position = "Advisory"` (`isAdvisory` in `lib/dance.ts`) gets `seesAllTeams` (also true for the SuperAdmin): team tabs on every Dance Floor page, read-only roster (`readOnly` on `RosterClient`, plus Export), team attendance overview, Team insights for any team, the committee Analytics "Dance Floor" tab and "Dancer reports (view only)". They NEVER get `canManage`, so every Dance Floor write API refuses them; no Import, no Review reports. Use `seesAllTeams` for READ checks and `canManage(team)` for WRITE checks.
- **Dance team isolation: ONLY the SUPERADMIN sees and manages every dance team** (plus Advisory read-only, above). Core/committee rights never extend to dance teams. `canManage(team)` = SuperAdmin, or a Lead for their own team. `pageTeam()` ignores `?team=` for everyone but the SuperAdmin. A Core member in a team is a Normal Dancer there (own team, view only); a Core member with no team cannot open the Dance Floor (sent to `/dashboard`) and has no Dance Floor button (`showDanceFloor` prop on `Sidebar`). The committee Analytics "Dance Floor" tab (`dance` is null for non-SuperAdmins) and the "Dancer reports (view only)" list are SuperAdmin only.
- **Who edits what.** Team Leaders edit their own team's PURE dancers from the Dance Floor roster (pencil -> `components/dance/EditDancerPanel.tsx`: name, register no, email/login, phone, programme, year, role, FFCS; a Lead cannot change their own role) via `PATCH api/members/[id]`, which re-checks the team server-side; for Core/Normal members who dance, a Lead only sets skill and FFCS. Every member edits their OWN phone, academic year and programme on **My details** (`app/account`, `PATCH api/account/details`, person-with-gear icon next to the password key in all three shells; `/programme` redirects there); name, register number, email, role and team stay with the committee/Lead. Editing an email on any form also changes the LOGIN email (`User.email`) and rejects duplicates with a clear message.
- Leads add/remove dancers (Normal Dancer or Team Leader) in their own team, set `skillLevel` (PROFESSIONAL | AMATEUR, default AMATEUR), create rehearsals and performances, and mark attendance (PRESENT/ABSENT/EXCUSED; % = present / (present + absent)).
- Dancers (`category = DANCER`) have **Reports only, no OD**. Normal dancers' reports are reviewed ONLY by their team's Lead; Dance Leads' own reports are reviewed by the committee. Nobody reviews their own.
- Notifications (`lib/notify.ts`, `notifyTeam`): when a Lead (or committee) creates a rehearsal, creates a performance, or FIRST saves attendance for a rehearsal, every dancer in that team plus every SuperAdmin gets a `Notification` (types `REHEARSAL_ADDED`, `PERFORMANCE_ADDED`, `ATTENDANCE_MARKED`, with a `link`). The person who did the action is not notified. A failed notification never fails the request. There are TWO separate feeds, worked out in `lib/notify.ts` (`sectionWhere`, no extra DB column): **Dance Floor** = the three team types above, or anything sent to a `DANCER` member (e.g. a dancer's report decision), shown at `/dance/notifications` (stage style, orange badge in `DanceSidebar`); **Working Committee** = everything else, shown at `/notifications` (console style, violet badge in the committee `Sidebar`). New committee types: `REPORT_SUBMITTED` (any report except a normal dancer's, which goes to their Lead), `OD_REQUESTED`, and `MEMBERS_ADDED` (an Excel import finished, or a Dance Lead added a dancer), all sent to SuperAdmins by `notifySuperAdmins`. Adding dancers to an existing performance notifies just those dancers (`notifyMembers`). **Cancelling** an UPCOMING rehearsal or performance (date today or later, IST) does NOT delete it: the DELETE routes (`api/dance/rehearsals/[id]`, `api/dance/performances/[id]`) set `cancelledAt` + `cancelledBy` (the canceller's name; nullable columns on `Rehearsal` and `Performance`, null = going ahead), so it stays in the history with a Cancelled badge, and notify everyone in that team plus SuperAdmins, minus whoever cancelled (types `REHEARSAL_CANCELLED` / `PERFORMANCE_CANCELLED`, Dance Floor feed; message names the item, date, time/venue and "your Team Leader, <name>" or "the Super Admin" via `cancelledBy()`). DELETE on a PAST or already-cancelled item really deletes it and notifies nobody. Cancelled items are excluded (`cancelledAt: null`) from the next rehearsal/performance on both dashboards, the Attendance list, committee and team analytics; attendance cannot be saved for a cancelled rehearsal and a cancelled performance's dancers cannot be changed (both APIs return 400). The SuperAdmin can also view normal dancers' reports read-only (`/reports/review`, "Dancer reports (view only)", `api/reports?scope=dancers`); only the team's Lead can decide them. `api/notifications` PATCH and `api/notifications/unread` accept `section=COMMITTEE|DANCE`. The SuperAdmin has a cross-link between the two pages.
- Every `/api/dance/*` and member/timetable/reports API re-checks the caller server-side with `getCaller()`. Never trust a team sent from the browser.
- Dance Floor access: the SuperAdmin, or anyone with a `team` (checked in `app/dance/layout.tsx`; middleware only requires login). The member portal shows a "Dance Floor" link to members with a team.
- Mixed teams: the roster shows non-dancers with a category badge. Leads can delete only pure dancers; for others the button is "Remove from team" (`PATCH api/dance/members/[id]/team`, sets `team = null`, keeps the account). Leads can read every teammate's timetable but edit only pure dancers'.
- Roster import/export/template (`api/dance/roster/import|export`) is SuperAdmin only, one team at a time. Import adds an existing account with no team to the team instead of skipping it.
- **Report topic** `Report.area` (`COMMITTEE` | `DANCE`, nullable for old reports). Pure dancers are always DANCE, members without a team always COMMITTEE, members with both pick on the form. "Lead-reviewed" = DANCE (or null from a pure dancer) and the submitter is not a Lead (`leadReviewedWhere` / `isLeadReviewed` in `lib/dance.ts`); those go to the team's Lead, everything else to the committee.

**OD**
- Only CORE and MEMBER categories can request OD (dancers cannot).
- An OD must be based on the member's own APPROVED report. One OD per report (`reportId` is unique).
- The member must pick an Event (`eventId`). Events are created by the SuperAdmin.
- Slots are stored as time-range strings. The member must pick an even number of slots, minimum 2.
- Status is PENDING, then APPROVED, set only by the SuperAdmin after the college grants the OD.

**FFCS grades**
- Grades are S/A/B/C/D/E (enum `FFCSGrade_Enum`).
- Only members with `isFFCS = true` appear on the grades page. Only the SuperAdmin can create, edit or delete grades.
